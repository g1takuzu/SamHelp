# Интеграция SamHelp ↔ amoCRM

## Выбранная модель

- Каждый сотрудник подключает собственный аккаунт amoCRM через OAuth 2.0.
- У одного пользователя SamHelp может быть одно подключение amoCRM.
- Один контакт SamHelp связан ровно с одной сделкой amoCRM.
- Новые записи создаются автоматически после проверки существующей связи.
- Синхронизация двусторонняя.
- История операций и уведомления хранятся в Supabase.

## Архитектура безопасности

Electron/renderer не получает OAuth access token, refresh token или service-role key.
Все обращения к amoCRM выполняются только серверными Supabase Edge Functions.
Таблицы amo-интеграции закрыты от ролей anon/authenticated; доступ к ним есть только у service_role.
Каждая функция, работающая от имени сотрудника, обязана проверить JWT и использовать user_id из проверенной сессии, а не из тела запроса.

## SQL

Применить миграцию:

`supabase/migrations/202611180001_amo_integration.sql`

Миграция создаёт:
- `amo_connections` — одно OAuth-подключение на пользователя;
- `amo_contact_links` — связь SamHelp contact ID ↔ amo contact/deal;
- `amo_stage_map` — сопоставление этапов;
- `amo_sync_jobs` — очередь синхронизации с дедупликацией;
- `amo_sync_events` — журнал событий;
- `samhelp_notifications` — уведомления сотрудника.

Таблицы закрыты для прямого доступа из клиента. Не открывайте их RLS-политиками для authenticated: чтение/запись выполняют Edge Functions с проверкой владельца.

## Переменные Supabase Functions

Настроить в Supabase Dashboard → Edge Functions → Secrets:

- `AMO_CLIENT_ID` — ID интеграции amoCRM;
- `AMO_CLIENT_SECRET` — секрет интеграции;
- `AMO_REDIRECT_URI` — точный callback URL зарегистрированной интеграции;
- `AMO_TOKEN_ENCRYPTION_KEY` — Base64 от случайных 32 байт для AES-GCM шифрования OAuth-токенов.

Callback URL зарегистрированной интеграции должен в точности совпадать с `AMO_REDIRECT_URI`. Для текущего проекта это URL функции `amo-oauth-callback` в Supabase, например `https://<project-ref>.supabase.co/functions/v1/amo-oauth-callback`.

Системные `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` предоставляет среда Supabase Functions. Никогда не добавляйте их секретные значения в GitHub или Electron.

## Развёртывание OAuth-основы

После применения миграции и настройки секретов:

1. Развернуть `amo-oauth-start` с JWT-проверкой включённой.
2. Развернуть `amo-oauth-callback` с JWT-проверкой выключенной: OAuth callback вызывается amoCRM, а не с пользовательским JWT. Защита callback обеспечивается одноразовым state.
3. Развернуть `amo-connection-status` с JWT-проверкой включённой.
4. Зарегистрировать callback URL в настройках интеграции amoCRM.

Эти функции пока не вызываются интерфейсом SamHelp: сначала необходимо подключить Supabase Auth к текущему экрану входа.

## Следующие этапы

1. Подключить фактическую Supabase Auth-сессию в интерфейсе SamHelp. Сейчас UI всё ещё содержит локальную авторизацию/локальное состояние; одна SQL-миграция не переносит пользователей и контакты в облако.
2. Добавить OAuth start/callback с одноразовым state, проверкой пользователя и шифрованием токенов.
3. Добавить endpoint для списка воронок/этапов и экран сопоставления статусов.
4. Реализовать создание сделки и сохранение уникальной связи.
5. Зарегистрировать webhook на аккаунт сотрудника и принимать события статусов.
6. Добавить обработчик очереди, журнал и уведомления.
7. После тестирования сделать перенос локальных контактов по владельцам.

## Важное ограничение текущего этапа

Эта миграция — серверная схема и основа безопасности, а не готовая синхронизация. До настройки OAuth credentials, развёртывания Edge Functions и подключения Supabase Auth кнопка подключения не должна показывать успешный статус.
